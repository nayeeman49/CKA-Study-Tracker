@@ 10-Design-and-Install-Kubernetes-Cluster/01-Designing-a-Kubernetes-Cluster
### Questions to ask first
1. **Purpose:** learning (Minikube/kind, single node), development/testing (multi-node kubeadm), or production (HA control plane, many workers).
2. **Cloud or on-prem?** Managed (EKS/GKE/AKS: the provider runs the control plane) vs self-managed (kubeadm, kubespray, Rancher).
3. **Workload:** how many apps, Pods and how much traffic, CPU/memory/GPU needs, persistent storage, network needs.

### Sizing guidance
- Documented limits: up to ~5,000 nodes, 150,000 Pods, 300,000 containers, 110 Pods per node.
- Production: **three** control-plane nodes behind a load balancer; etcd on fast SSD; separate worker pools by workload (general, memory heavy, GPU).
- Keep user workloads off control-plane nodes (default taint).
- Use a minimal Linux with containerd.

### What to produce
A short design: node counts/sizes, topology (stacked or external etcd), CNI choice, storage classes, ingress approach, upgrade and backup plan.

@@ 10-Design-and-Install-Kubernetes-Cluster/03-Configure-High-Availability
### The design
- **API server:** stateless and active-active: run one per control-plane node and put a **load balancer** (HAProxy/nginx/cloud LB) in front. Clients use the LB address (`--control-plane-endpoint`).
- **Scheduler and controller manager:** active/passive via **leader election**: `--leader-elect=true` uses a Lease; others take over if the leader's lease expires.
- **etcd:** 3 or 5 members (stacked on the control plane or external).

### How to do it (kubeadm)
```
kubeadm init --control-plane-endpoint "LB_DNS:6443" --upload-certs --pod-network-cidr=10.244.0.0/16
# on other control-plane nodes:
kubeadm join LB_DNS:6443 --token ... --discovery-token-ca-cert-hash sha256:... --control-plane --certificate-key ...
```
### Verify
`kubectl get nodes` lists all control-plane nodes; `kubectl -n kube-system get lease` shows the leaders; stopping one API server doesn't break `kubectl`.

### Watch out
The load balancer must exist **before** `kubeadm init`. Use an odd number of control-plane nodes.

@@ 10-Design-and-Install-Kubernetes-Cluster/04-ETCD-in-HA
### Concepts
etcd uses **Raft**: one leader, writes need acknowledgement from a majority (**quorum = ⌊N/2⌋ + 1**).

| Members | Quorum | Failures tolerated |
|---|---|---|
| 1 | 1 | 0 |
| 2 | 2 | 0 (worse than 1) |
| 3 | 2 | 1 |
| 5 | 3 | 2 |
Use 3 (minimum HA) or 5; odd numbers are best; more than 7 slows writes. Spread members across failure domains.

### Topologies
- **Stacked:** etcd runs on each control-plane node (kubeadm default); simplest, but losing a node loses both.
- **External:** a separate etcd cluster; more machines but more isolated.

### Commands
```
etcdctl member list --write-out=table --endpoints=https://127.0.0.1:2379 --cacert=... --cert=... --key=...
etcdctl endpoint health --cluster
etcdctl endpoint status --cluster --write-out=table      # who is the leader
```
### Watch out
Before maintenance never remove a node that breaks quorum. Back up regularly.

@@ 12-Troubleshooting/04-Control-Plane-Failure
### Method
1. **Nodes and system Pods:** `kubectl get nodes`, `kubectl get pods -n kube-system`. On kubeadm clusters the control plane runs as static pods named `<component>-<node>`.
2. **Read the failing component:** `kubectl describe pod kube-scheduler-controlplane -n kube-system`, `kubectl logs ... -n kube-system`.
3. **If `kubectl` itself fails** (API down): `crictl ps -a`, `crictl logs <id>`; `journalctl -u kubelet`.
4. **Fix the manifest** in `/etc/kubernetes/manifests/` (wrong command name, image, flag, kubeconfig path, certificate path, volume host path). The kubelet recreates the Pod.
5. Non-kubeadm clusters: `systemctl status kube-apiserver` and `journalctl -u kube-apiserver`.

### Symptoms → suspects
- New Pods stay Pending, no events → **scheduler**.
- Deployment creates no Pods/ReplicaSets, scaling does nothing → **controller-manager**.
- `kubectl` connection refused/timeouts → **API server or etcd**.
- API server logs about etcd → check etcd Pod, certs and `--etcd-servers`.

### Watch out
Typos in file paths inside manifests are the classic injected bug (e.g. `/etc/kubernetes/scheduler.conf` vs `/etc/kubernetes/scheduler-xyz.conf`, or a hostPath for certificates).

### How to do it

@@ 13-Other-Topics/02-Pre-Requisites-JSON-PATH
### Concepts
JSON is `key: value` pairs, arrays `[...]` and nested objects. JSONPath addresses data: `$` root, `.key` child, `[n]` index, `[*]` all elements, `[?(@.x==1)]` filter, `..` recursive. In kubectl the `$` is implied and the path goes inside braces: `'{.items[*].metadata.name}'`.

### Examples
```
kubectl get nodes -o jsonpath='{.items[*].status.nodeInfo.osImage}'
kubectl get pods -o jsonpath='{.items[?(@.status.phase=="Running")].metadata.name}'
kubectl get pods -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.podIP}{"\n"}{end}'
kubectl get nodes -o jsonpath='{.items[*].metadata.name}{"\n"}{.items[*].status.capacity.cpu}'
```
### Practise
Write queries against any JSON file with `jq` too: `kubectl get pods -o json | jq '.items[].metadata.name'`.

### Watch out
Use single quotes around the whole expression and double quotes inside. Arrays of results are space separated; add `{"\n"}` or `range` for lines.
